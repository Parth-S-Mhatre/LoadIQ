## ⚙️ Setup

### 1. Install dependencies

```bash
cd Backend
pip install fastapi uvicorn lightgbm xgboost scikit-learn numpy pandas joblib firebase-admin
```

Or with a requirements file:

```bash
pip install -r requirements.txt
```

**requirements.txt**
```
fastapi>=0.100.0
uvicorn>=0.23.0
lightgbm>=4.0.0
xgboost>=2.0.0
scikit-learn>=1.3.0
numpy>=1.24.0
pandas>=2.0.0
joblib>=1.3.0
firebase-admin>=6.0.0
python-multipart>=0.0.9
pypdf>=5.0.0
```

### 2. Generate model artifacts

**Model1 (DE+LU)** uses the six original artifacts generated by the
training notebook (`../DATA_preprocessing/Modelling/`):

```
lgb_load_model.pkl       ← LightGBM primary model
xgb_load_model.pkl       ← XGBoost secondary model
ridge_load_model.pkl     ← Ridge regression baseline
X_scaler.pkl             ← MinMaxScaler (used only for Ridge)
feature_names.pkl        ← Ordered list of all 55 feature names
train_medians.pkl        ← pd.Series of training medians for missing-value fill
```

**Model2 (GB)** uses dedicated `_gb` artifacts. Rebuild them from the raw OPSD
extract with the reproducible script:

```bash
# From the repository root
python Backend/train_gb_artifacts.py
```

This reads `DATA/energy_30min_processed.csv`, resamples to hourly values,
builds lag/rolling/calendar features and writes to `Backend/Model_assets/`:

```
lgb_gb_model.pkl         ← LightGBM primary model
xgb_gb_model.pkl         ← XGBoost secondary model
ridge_gb_model.pkl       ← Ridge regression baseline
X_scaler_gb.pkl          ← MinMaxScaler (used only for Ridge)
feature_names_gb.pkl     ← Ordered feature names
train_medians_gb.pkl     ← Training medians for missing-value fill
model_metadata_gb.json   ← Holdout metrics + training window
```

> ⚠️ **Model2 will not fall back to the DE/LU artifacts.** If the `_gb` files
> are missing, the service reports `artifact_mode: "fallback_non_gb"` and
> prediction endpoints return HTTP `503`. Set `ALLOW_NON_GB_FALLBACK=true`
> only for a deliberate local experiment; it is not safe for production because
> the endpoint would return DE-scale predictions.

### 3. Run the servers

```bash
# Terminal 1
python Model1.py     # http://localhost:8001

# Terminal 2
python Model2.py     # http://localhost:8002
```

### 4. Verify startup

```bash
curl http://localhost:8001/health
curl http://localhost:8002/health
```

**Expected response:**
```json
{
  "status": "ok",
  "models_loaded": ["lightgbm", "xgboost", "ridge", "ensemble"],
  "feature_count": 55,
  "default_model": "ensemble"
}
```

`GET /model2/health` additionally reports the artifact state:

```json
{
  "status": "ok",
  "artifact_mode": "gb",
  "gb_artifacts_available": true,
  "allow_non_gb_fallback": false,
  "models_available": ["lightgbm", "xgboost", "ridge", "ensemble"]
}
```

The Model2 service loads artifacts lazily, so `models_loaded` can be empty
until the first prediction. Use `models_available` for readiness checks.

## 🔌 API Reference — Model2.py (Port 8002)

**Target:** `GB_GBN_load_actual_entsoe_transparency` — Great Britain electricity demand (MW)

### POST `/predict`

Single-step prediction. Accepts same structure as Model1 plus `last_24_hours`.

```json
{
  "hour": 14,
  "day_of_week": 2,
  "month": 6,
  "model": "ensemble",
  "last_24_hours": [27500, 27800, 28100, 28400, 28200, 28000,
                    27900, 27700, 27600, 27500, 27800, 28100,
                    28500, 28900, 29100, 29000, 28800, 28500,
                    28200, 27900, 27600, 27400, 27200, 27000]
}
```

> **Tip:** Providing `last_24_hours` auto-populates all lag features (`load_lag_1h`, `load_lag_24h`, `load_rolling_mean_24h`, etc.) for maximum accuracy.

### POST `/predict_batch`

Multi-step iterative forecast up to 168 steps (1 week) ahead.
Each predicted value automatically feeds into the next step's lag features.
Pass `hour`, `day_of_week` and `month` to anchor the forecast to a real
calendar; without them the server uses the current UTC time and advances the
calendar at each step.

```json
{
  "last_24_hours": [27500, 27800, 28100, 28400, 28200, 28000,
                    27900, 27700, 27600, 27500, 27800, 28100,
                    28500, 28900, 29100, 29000, 28800, 28500,
                    28200, 27900, 27600, 27400, 27200, 27000],
  "horizon": 24,
  "model": "ensemble",
  "hour": 14,
  "day_of_week": 2,
  "month": 6
}
```

**Response:**
```json
{
  "horizon": 24,
  "predictions": [
    { "step": 1, "predicted_load_mw": 27850.20, "model_used": "ensemble", "fallback_used": false },
    { "step": 2, "predicted_load_mw": 28120.40, "model_used": "ensemble", "fallback_used": false }
  ],
  "prediction_source": "ensemble",
  "fallback_used": false
}
```

## 📄 API Reference — Documents (PDF bills)

The document MVP extracts electricity-bill data, keeps evidence for every
field, and produces charts, insights and recommendations. It is mounted on the
combined backend at the same origin as `/model1` and `/model2`.

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/documents` | Upload a digital PDF (multipart field `file`) |
| `GET` | `/documents` | List the caller's documents |
| `GET` | `/documents/{id}` | Poll processing status |
| `GET` | `/documents/{id}/extraction` | Extracted fields + evidence |
| `POST` | `/documents/{id}/confirm` | Accept/correct fields (`{"fields": {...}}`) |
| `GET` | `/documents/{id}/analytics` | Summary, charts, insights, recommendations |
| `GET` | `/documents/{id}/report` | Self-contained HTML report |
| `DELETE` | `/documents/{id}` | Delete the document and stored file |

### Example

```bash
curl -X POST http://localhost:8000/documents \
  -H "X-User-ID: demo-user" \
  -F "file=@bill.pdf"

curl http://localhost:8000/documents/<id>/analytics \
  -H "X-User-ID: demo-user"
```

### Evidence model

Every extracted value keeps `page`, `line`, `source_text`, `method` and
`confidence`. Insights and recommendations reference the evidence IDs, so the
report can show exactly which line of the bill supports each claim.

### MVP limitations

- **Digital PDFs only.** Scanned bills are detected (low text layer) and
  flagged; OCR is not enabled.
- **SQLite + local files.** The store lives in `Backend/data/` and is
  ephemeral on Render. Use PostgreSQL and object storage before production.
- **BackgroundTasks, not a durable queue.** A restart during processing leaves
  the document in `processing`; re-upload in that case.
- **Review is required.** Extraction is regex-based and marks uncertain fields
  `needs_review`; confirm them before acting on the analysis.

### Documents environment variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `DOCUMENTS_AUTH_MODE` | `none` | `none`, `header` or `firebase` |
| `DOCUMENTS_DB_PATH` | `Backend/data/documents.db` | SQLite file |
| `DOCUMENTS_STORAGE_DIR` | `Backend/data/documents` | Uploaded PDFs |
| `DOCUMENTS_MAX_UPLOAD_BYTES` | `15728640` (15 MB) | Upload limit |

> `DOCUMENTS_AUTH_MODE=none` is for local development only. Use `header`
> (requires `X-User-ID`) or `firebase` (verifies `Authorization: Bearer
> <Firebase ID token>`) in any shared environment.

## 🛡️ Error Handling & Fallback

Both servers have three layers of protection:

**Layer 1 — Input validation**
Pydantic validators reject invalid `hour` (0–23), `day_of_week` (0–6), `month` (1–12) before the model runs.

**Layer 2 — Median fill**
Any missing feature is filled with the training-set median automatically. The model never receives zeros for missing values.

**Layer 3 — Heuristic fallback (Model2 only)**
If the ML model raises an exception for an individual step during batch prediction, a weighted heuristic using `recent_mean`, `daily_anchor`, and `momentum` returns a reasonable estimate. The response flags `"fallback_used": true` so the frontend can display a warning.

**Layer 4 — Strict GB artifact guard (Model2 only)**
The heuristic fallback never masks a missing deployment artifact. If only the
legacy DE/LU `.pkl` files are present, Model2 raises `503` and reports
`artifact_mode: "fallback_non_gb"` rather than returning DE-scale values from
the GB endpoint.

## 🔒 Security Notes

- CORS defaults to localhost origins in development. Set `FRONTEND_ORIGINS` (comma-separated) or `FRONTEND_ORIGIN` to your production frontend domain.
- Firebase credentials are loaded from environment variable `FIREBASE_SERVICE_ACCOUNT_JSON` or `serviceAccountKey.json`. Never commit `serviceAccountKey.json` to Git.
- Model2 refuses to serve the DE/LU artifacts from the GB endpoint. Keep `ALLOW_NON_GB_FALLBACK` unset in production.
- The documents store is unauthenticated by default (`DOCUMENTS_AUTH_MODE=none`). Set it to `firebase` or `header` before exposing `/documents` publicly.
- Uploaded PDFs and the SQLite database live under `Backend/data/`, which is gitignored and ephemeral on Render.

## 📊 Model Performance

| Metric | Ridge | XGBoost | LightGBM | Ensemble |
|--------|-------|---------|----------|----------|
| R² | ~0.94 | ~0.98 | ~0.99 | ~0.99+ |
| MAPE | ~4% | ~2% | ~1.2% | **< 1.5%** |
| Speed | Fastest | Medium | Fast | Medium |

*Measured on DE+LU 60-min dataset, 20% chronological test set.*

### GB Model2 artifacts

Trained by `train_gb_artifacts.py` on 50,374 hourly rows
(2015-01-01 → 2020-09-30, chronological 80/20 split). Holdout metrics in
`Model_assets/model_metadata_gb.json`:

| Model | MAE (MW) | RMSE (MW) | MAPE |
|-------|----------|-----------|------|
| LightGBM | 950.93 | 1469.17 | 3.341% |
| Ensemble (0.6 LGB + 0.4 XGB) | 959.62 | 1496.44 | 3.378% |

These are in-sample-window holdout scores, not a guarantee for future or
out-of-distribution inputs. Model2 is lag-driven; the calendar features have a
smaller effect than the 24-hour load history.
